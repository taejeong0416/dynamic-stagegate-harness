# 구조 설계

이 문서는 preset 대신 부품과 적용 조건으로 하네스를 조립하고, 게이트와 기록이 작업이 쌓여도 관리되도록 하는 구조를 정한다. 검토가 끝나면 구현 순서대로 나눠 반영하고, 반영한 부분은 README.md와 GATE.md로 옮긴다.

## 풀려는 문제

첫 사용처인 수업 대회 저장소(이하 대회 하네스, 2026-11-05부터 계획 20개)에서 드러난 문제다.

| 문제 | 근거 |
|---|---|
| preset 하나를 통째로 고르는 구조라 용도가 섞인 프로젝트를 담지 못한다 | ml preset에 서비스 코드의 테스트 우선 검사를 더하려면 상태와 절을 하나씩 빌려야 하고, 그 기능을 받치는 검사가 같이 따라오는지는 보장되지 않는다 |
| 일반화하면서 프로젝트 고유의 게이트를 잃었다 | 대회 하네스의 종류 재판정, IDEATE 축 검사, 위키 커밋 검사, audit 종류, watch_chain 감시가 ml preset에 없다. 이 게이트들은 대부분 실제 사고에서 나왔다(사슬 19시간 멈춤, 결측 형태와 GPU 메모리 누락, 무효 실험 5건) |
| 복사한 뒤에는 출처가 남지 않는다 | 라이브러리가 고쳐져도 프로젝트에 제안할 수 없고, 프로젝트에서 자란 게이트를 라이브러리로 올릴 수도 없다 |
| 기록이 시간에 비례해 커지고 에이전트가 원본을 읽는다 | 대회 하네스의 상태 파일은 계획 20개에 93KB, 결정 문서는 2주에 64KB, 현재 상태 문서는 24,000자까지 커져 SessionStart 출력이 한도를 넘었다 |
| 진단이 마찰만 잰다 | 검토 32회 중 FAIL은 1회였는데 통과 뒤 드러난 결함은 5건이었다. 지금 diagnose로는 이 차이가 보이지 않아, 마찰 수치만 근거로 구조가 느슨해지기 쉽다 |

## 설계 원칙

- 전이 조건은 결정적 검사로 판정하고, LLM 판단은 읽기 전용 검토자로 한정한다.
- 규칙(엔진, 부품, 조립 결과)은 프로젝트 git에 복사한다. 나중에 다시 실행해도 같은 규칙이 적용되고, 플러그인이 바뀌어도 프로젝트 규칙은 승인 없이 바뀌지 않는다.
- 복사한 조각마다 출처와 버전을 남긴다. 갱신과 역류는 이 기록으로 제안서를 만들어 한다.
- 에이전트가 한 번에 읽는 양은 작업이 쌓여도 일정해야 한다. 원본은 쌓이되 에이전트는 크기가 고정된 보기를 읽는다.
- 구조를 바꾸는 모든 일(부품 추가와 제거, 게이트 생성과 완화, 기록 압축 규칙)은 진단, 제안서, 검사, 승인, adopt라는 한 경로를 지난다.
- 계획의 상태 경로는 조건부 건너뜀과 적어 둔 되돌아가는 경로를 가진 선형 경로로 둔다.

## 부품

미리 만들어 두는 단위는 preset이 아니라 부품이다. 부품은 이름과 버전이 붙은 묶음이고, 하나의 기능을 이루는 상태, 절, 검사, 설정을 함께 담는다. 예를 들어 실행 기록 부품(run-record)은 실행 상태의 run 표시, run 기록 검사, 실행 상태 뒤 코드 변경 검사, 학습 서버 설정을 한꺼번에 담는다. 기능을 뒷받침하는 검사가 빠진 채 상태만 들어오는 일을 막기 위해서다.

라이브러리 부품은 플러그인의 `library/<이름>/part.toml`에 있고, 설치하면 전부 `.gate/library/`에 복사된다. 프로젝트가 쓰는 부품은 `.gate/parts/<이름>/part.toml`이다. 검사 모듈 `checks.py`와 hook 규칙(guard, stop)을 부품에 담는 일은 사고 기록 단계에서 project 부품과 함께 넣는다.

| 키 | 뜻 |
|---|---|
| name, description, version | 부품 이름, 한 줄 설명, 버전 |
| origin | library(라이브러리에서 복사), project(이 프로젝트에서 만듦) |
| provenance | project 부품이면 만든 계기(사고 기록 ID, 날짜, 증거 경로) |
| applies_when | 이 부품이 필요한 조건(아래 "적용 조건") |
| requires, conflicts | 함께 있어야 하는 부품과 같이 둘 수 없는 부품 |
| covers | 이 부품이 잡으려는 결함 분류(아래 "게이트 수명 주기") |
| [project], [remote], [review], [[stages]] | 조립 결과에 더하는 설정. 목록은 합치고, 값 하나짜리 키를 두 부품이 다르게 정하면 조립 문제다 |
| [kinds], [states], [sections] | 종류와 그 상태 경로, 상태, 절의 정의. 종류를 정하는 부품이 경로 부품이다 |
| [[attach]] | 역할이나 이름이 맞는 상태에 더하는 절, 할 일, 검사, 검토 |
| [[insert]] | 새 상태를 넣는 자리. `before`나 `after`에 역할을 적는다 |

### 경로 부품과 역할

종류별 상태 경로는 경로 부품이 정한다. 라이브러리에는 실험 경로(experiment), 측정 경로(measure), 공용 코드 경로(infra), 기능 경로(feature), 결함 경로(bugfix), 작은 변경 경로(chore), 에이전트 경로(eval)가 있다. 경로 부품은 상태에 역할(plan, implement, execute, verify, record, decide)을 붙인다. 상태 하나가 역할을 여러 개 가질 수 있고, 역할이 없는 상태도 있다.

다른 부품은 역할에 붙는다. 코드 diff 검토 부품(diff-review)은 `after = "verify"`로 확인 상태 뒤에 REVIEW를 넣어서, 기능 경로의 TEST 뒤와 결함 경로의 VERIFY 뒤에 같은 상태가 들어간다. 뒤에 넣은 상태는 앞 상태의 back 경로를 물려받는다. 실행 기록 부품은 `roles = ["execute"]`로 실행 상태에 검사를 더한다. 한 계열 안에서만 뜻이 있는 부품은 `states = ["TEST"]`처럼 상태 이름에 붙는다.

attach와 insert의 `only`, `skip`은 종류 이름이다. attach는 대상 상태를 쓰는 종류 가운데 통과하는 것이 하나도 없으면 그 상태에 붙지 않는다. 검사마다 적용할 종류는 검사 자신의 `only`, `skip`으로 적는다.

상태와 절의 이름은 조립 결과 전체에서 하나다. 두 부품이 같은 이름을 똑같이 정의하면 함께 쓰고, 다르게 정의하면 조립 문제다. 검토 지시문(review)은 상태마다 한 부품만 정한다.

### 조립

조립은 부품 목록과 프로젝트 덮어쓰기(`.gate/local.toml`)에서 `.gate/config.toml`을 만든다. 엔진은 config.toml만 읽는다. 같은 입력이면 같은 결과가 나와야 하므로 순서 규칙을 고정한다.

- 부품은 경로 부품, library 부품, project 부품 순으로, 같은 묶음 안에서는 이름 순으로 쌓는다.
- 상태에 더하는 내용은 attach의 `at` 값(기본 50, 상태 정의도 50) 순으로 잇고, 값이 같으면 위의 부품 순서를 따른다.
- 종류는 부품 순서대로, 상태는 종류의 경로에 나오는 순서대로, 절은 상태가 쓰는 순서대로 적는다.

local.toml의 `[project]`, `[remote]`, `[review]`는 키 단위로, `[kinds]`, `[states]`, `[sections]`는 이름 아래 필드 단위로 조립 결과를 덮어쓴다. 폴더 패턴이나 서버 주소처럼 프로젝트마다 다른 값을 여기에 둔다.

`.gate/parts.lock`에는 조립에 쓴 부품의 버전, 출처, 파일 해시와, 라이브러리에서 복사할 때의 해시(from)를 남긴다. 부품 파일의 해시가 from과 같으면 프로젝트에서 고치지 않은 부품이라, 라이브러리 버전이 오르면 그대로 바꿔 넣을 수 있다. 계획은 시작할 때의 구조 버전을 기록하고, 그 버전의 조립 결과(`.gate/history/`)를 끝날 때까지 쓴다.

조립과 lint는 다음을 문제로 본다.

- 두 부품이 같은 종류, 상태, 절을 다르게 정의하거나 같은 설정 키를 다르게 정한다
- requires가 빠졌거나 conflicts가 함께 있다
- insert가 넣을 자리나 attach가 붙을 상태가 없다
- config.toml이 부품과 local.toml을 조립한 결과와 다르다

parts 폴더가 없는 프로젝트는 config.toml 전체를 구조의 원본으로 보고 지금처럼 돌아간다.

### 계열 사이의 이름 충돌

지금 라이브러리의 실험 계열, 서비스 계열, 에이전트 계열은 한 프로젝트에 함께 조립되지 않는다. 실험 경로와 기능 경로를 함께 넣으면 PLAN, IMPLEMENT, RECORD 상태와 "기록" 절을 서로 다르게 정의하고, `[project]`의 plans_dir과 files_section 값이 달라서 조립 문제가 6건 나온다. 계열을 섞으려면 한쪽 계열의 상태와 절 이름을 바꾸고 files_section을 종류별로 둘 수 있게 해야 한다. 이름이 바뀌면 계획 틀과 문서의 용어가 달라지므로, 실제로 섞어 쓸 프로젝트(대회 하네스 이전)가 생길 때 제안서로 정한다.

## 적용 조건

적용 조건은 검사가 판정할 수 있는 사실로만 쓴다. 같은 저장소와 같은 답이면 같은 부품이 조립되어야 하기 때문이다.

| 조건 키 | 판정 |
|---|---|
| file | 저장소에 glob에 맞는 파일이 있다 |
| command | 명령이 성공한다(예: 테스트 목록 수집 명령) |
| answer | 고정 질문에 이 답을 했다. 답이 여러 개인 질문은 그중 하나가 맞으면 된다 |
| not, any, all | 조건의 부정, 하나 이상, 모두 |

고정 질문의 답은 `.gate/local.toml`의 `[answers]`에 둔다. 자유 서술 인터뷰는 지금처럼 PROFILE.md에 남는다.

| 질문 | 키 | 답 |
|---|---|---|
| 이 저장소에서 하는 일 | work | experiment(지표로 비교하는 실험), service(서비스나 라이브러리 코드), agent(에이전트, 프롬프트). 여러 개를 고를 수 있다 |
| 오래 걸리는 실행을 어디서 돌리는가 | run | local, remote |
| 산출물을 밖으로 내보내는가(제출, 배포, 릴리스) | ships | yes, no |
| 테스트 명령이 있는가 | tests | yes, no |
| 실패하면 무엇을 잃는가 | failure_cost | reversible(되돌릴 수 있음), time(시간 손실), irreversible(되돌릴 수 없음) |

설치는 조건이 맞은 부품과, 맞지 않아 뺀 부품과 그 조건을 출력한다(`--dry-run`은 출력만 한다). 사용자가 목록을 승인하면 설치한다. diagnose는 조건을 다시 판정해서, 쓰지 않는 라이브러리 부품 가운데 조건이 참인 것과 쓰는 부품 가운데 조건이 거짓인 것을 보인다. 앞의 것은 추가 제안서로, 뒤의 것은 제거 제안서로 이어진다.

실제로 돌아 본 조합은 고르는 메뉴가 아니라 시험 자료로 둔다. `tests/combos/`에 조합마다 답과 기대 구조를 두고, 그 답으로 조립한 결과가 기대 구조와 같은지 시험한다. 대회 하네스를 옮긴 뒤에는 그 저장소의 답과 조립 결과도 여기에 더한다.

### 구조를 바꾸는 제안서

부품을 쓰는 프로젝트의 제안서는 새 config 전체가 아니라 새 입력을 담는다. `gate propose H###`가 지금 parts 폴더와 local.toml을 `.gate/proposals/H###/`에 복사하고, 에이전트는 그 사본에서 부품을 더하고 빼고 고친다. check-proposal은 사본을 조립해서 지금 구조와 견주고, lint, 푸는 변경 목록, 지난 계획 재생, 부품별 변경(더함, 뺌, 고침)을 진단 파일에 쓴다. adopt는 앞 구조를 history에 남기고 parts 폴더, local.toml, config.toml, parts.lock을 사본의 것으로 바꾼다.

## 게이트 수명 주기

게이트는 사고에서 만든 project 부품이다. 생기고, 성적에 따라 강화되거나 완화되고, 조건이 사라지면 빠진다.

### 사고 기록

게이트의 근거가 되는 사고는 세 곳에서 기록된다.

- back: `back --why`에 결함 분류(`--defect logic|data|resource|env|plan`)를 함께 받는다.
- 결과 판정: 기록 상태의 결과 칸이 무효나 결함이면, 그 결함이 지나간 상태를 함께 적는다.
- 사용자 지적: 에이전트가 `gate incident --defect ... --quote "..."`로 적는다. 인용문은 그 턴 사용자 입력에 있어야 한다.

hook이 막은 기록에는 나중에 판정을 붙인다. 막힌 뒤 같은 턴에 계획 파일이나 코드를 고치고 통과했으면 진짜 막힘으로, 하네스 파일을 고치거나 같은 명령이 하네스 수정만으로 통과했으면 오탐으로 본다. 어느 쪽인지 알 수 없으면 미판정으로 두고 diagnose에서 사용자에게 보인다.

### 성적

부품마다 성적을 쌓는다. 성적은 막은 횟수, 진짜 막힘, 오탐, 그 부품의 covers에 해당하는 결함이 부품을 지나 새어 나간 횟수, 검토 호출 비용이다. 이벤트 기록을 돌려써도 성적은 `.gate/scorecard.json`에 집계로 남는다.

### 제안 규칙

diagnose는 성적으로 아래 제안서 초안을 만든다. 기준값은 처음에는 근거 없이 정한 값이고 진단에 같이 보인다.

| 제안 | 조건 |
|---|---|
| 생성 | 같은 결함 분류가 서로 다른 계획에서 2번 이상 나왔는데 covers가 그 분류인 부품이 없다 |
| 강화 | covers가 그 분류인 부품을 지나 결함이 1번 이상 새어 나갔다 |
| 완화 | 최근 계획 10개에서 오탐이 3번 이상이고 진짜 막힘이 0번이다 |
| 제거 | applies_when이 거짓이 됐다 |

생성 제안서는 에이전트가 검사 코드와 provenance를 쓰고, 재생(아래 "구조 변경 검사")으로 그 사고를 낸 지난 계획을 실제로 막는지 보인다. 이렇게 사고를 다시 막는지 확인해야 형식만 채운 게이트를 거를 수 있다.

### 라이브러리로 올리기

project 게이트가 진짜 막힘을 3번 이상 냈고 프로젝트 고유의 경로와 이름을 설정으로 뺄 수 있으면, 라이브러리로 올리는 제안을 만든다. 올리는 일은 플러그인 저장소의 커밋이라 사용자가 승인한다. 라이브러리 부품의 버전이 오르면, 그 부품을 쓰는 프로젝트는 다음 diagnose에서 갱신 제안서를 받는다.

## 기록 수명 주기

기록은 역할별로 나누고, 역할마다 크기와 닫는 규칙을 정한다. 설정의 `[records]`에 파일과 역할을 적는다.

| 역할 | 예 | 규칙 |
|---|---|---|
| current | 현재 상태 문서 | 크기 상한이 있고 열린 항목만 둔다. 항목마다 고정 ID를 붙이고, 닫힌 항목은 archive로 옮긴다 |
| ledger | 실험 기록, 결정 문서 | 덧붙이기만 한다. 항목마다 ID와 대체 표시(superseded_by)를 두고, 보기에는 살아 있는 항목만 나온다 |
| work | 계획 파일 | 닫히면 색인(`plans/INDEX.md`)에 한 줄(번호, 제목, 종류, 결과, 실험 번호, 고른 갈래)을 더한다. 파일 경로는 바꾸지 않아 참조가 깨지지 않는다 |
| state | 상태 파일 | 닫힌 계획은 `state-archive.jsonl`로 옮겨 state.json에는 진행 중인 계획만 둔다 |
| events | 막힘 기록 | 크기 상한에서 돌려쓰고, 성적은 scorecard에 남긴다 |
| archive | 진행 경과 | 크기 제한이 없다. 보기에 넣지 않고 Grep으로 찾는다 |

### 보기

에이전트가 읽는 것은 하네스가 만든 보기다. 보기는 `[views]`에 출처와 크기 상한을 적고, 상한을 넘으면 오래된 것부터 줄인다.

- 세션 보기: 진행 중인 계획과 할 일, current 문서의 항목 머리, 게이트 알림(점검 권장, 재현 미확인, 계획 큐 상위)
- 검토 보기: 상태별 발췌(그 계획이 인용한 ID의 원장 행, 살아 있는 결정의 제목과 결론, 가리키는 current 항목)
- 계획 보기: 그 계획이 쓰는 절과 인용한 항목

### 구조화된 사실

검사가 읽어야 하는 사실(프로젝트 단계, 다음 실험 번호, 산출물 최고 점수, 비교 기준)은 문장이 아니라 current 문서 머리의 필드에 둔다. 정합성 검사는 이 필드를 원장과 견준다(예: 다음 실험 번호와 실험 기록의 마지막 번호). 대회 하네스처럼 문장을 정규식으로 찾지 않아서, 문서를 다시 써도 검사가 깨지지 않는다.

### 닫을 때 옮기기

기록 상태와 재계획 상태의 전이 조건에 기록 정리를 넣는다. 그 계획을 다룬 current 항목은 닫히거나 갱신되어 있어야 하고, 결정을 바꿨으면 옛 결정에 대체 표시가 있어야 하며, 계획 색인에 행이 있어야 한다. 쌓인 뒤에 한꺼번에 치우지 않고 닫을 때마다 옮기게 하기 위해서다.

### 정리 종류

정리 경로는 측정, 정리, 확인 세 상태다. current 문서나 state 파일이 상한을 넘거나 마지막 정리 뒤 계획 10개가 닫히면 SessionStart가 정리를 권한다.

- 측정: 파일 크기, 살아 있는 항목 수, 풀리지 않는 참조를 잰다.
- 정리: 에이전트가 닫힌 항목을 옮기고, 대체 표시를 붙이고, 색인을 만든다.
- 확인: 정리 전에 풀리던 참조(실험 번호, 계획 번호, 결정 제목, 파일 경로)가 정리 뒤에도 모두 풀리고, 정리 전 current 문서의 항목 ID가 current나 archive에 모두 있으며, 상한을 지켜야 넘어간다.

## 구조 변경 검사

부품, 게이트, 기록 규칙의 변경은 모두 제안서로 하고, check-proposal이 세 가지를 본다.

- 푸는 변경: 조립 결과의 모든 설정 키를 비교해 검사, 상태, 범위, 검토 강도를 줄이는 변경을 목록으로 만든다. 목록의 변경마다 진단 수치 근거가 있어야 한다.
- 재생: 닫힌 계획을 기록한 커밋의 파일(git show로 읽는다)에 새 조립 결과의 검사를 돌린다. 그 결과로 새로 막히는 지난 계획과 더는 막히지 않는 지난 계획을 보인다. 사고를 낸 계획이 막히면 좋은 신호이고, 문제없던 계획이 막히면 오탐 위험이다.
- 버전 고정: 진행 중인 계획은 시작할 때의 구조 버전을 쓰고, 엔진이 바뀌면 status와 SessionStart가 알린다.

## 대회 하네스 이전

대회 저장소(마감 2026-12-06)는 마감까지 자체 하네스를 쓰고, 마감 뒤 이 구조의 첫 실사용 사례로 옮긴다. 이전은 이 설계를 검증하는 시험이다.

1. 대회 하네스의 게이트를 부품으로 옮기는 대조표를 만든다. 종류 재판정은 경로 조건 확장(바뀐 파일과 diff 패턴), 축 검사는 표 칸 값 목록 검사, 위키 커밋 검사는 표에 적은 경로가 상태 진입 뒤 커밋됐는지 보는 검사, watch_chain은 원격 실행 부품의 stop 규칙으로 옮긴다. 옮기지 못하는 게이트는 project 부품의 checks.py로 둔다.
2. 대회 저장소의 사실과 인터뷰 답으로 조립하고, 대회 하네스와 같은 게이트가 모두 들어오는지 본다.
3. 계획 20개를 재생해 대회 하네스와 같은 지점에서 막히는지 본다.
4. 기록을 역할별로 나누고 정리 종류를 한 번 돌려 참조가 모두 풀리는지 본다.

## 하지 않는 것

- 상태 경로를 일반 그래프로 바꾸지 않는다. lint, back, 푸는 변경 분석, 재생이 선형 순서를 전제한다.
- 엔진에 상주 스케줄러나 자율 실행기를 넣지 않는다. 계획 순서는 큐 파일과 검사로만 다룬다.
- 전이 판단을 LLM 검토에 더 맡기지 않는다. 검토자 FAIL률이 낮은 지금은 결정적 검사를 늘리는 편이 비용과 신뢰 모두에서 낫다.
- 플러그인을 실행 중에 참조하지 않는다. 엔진과 부품은 계속 프로젝트 git에 복사한다.
