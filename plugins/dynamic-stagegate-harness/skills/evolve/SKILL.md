# 하네스 구조 다시 짜기

구조를 바꾸는 길은 제안서 하나뿐이다. `.gate/config.toml`은 guard가 직접 편집을 막는다.

## 1. 진단

1. `python -X utf8 .gate/gate.py diagnose`를 돌린다. 상태별 기록, hook이 막은 기록, 저장소 변화가 나온다.
2. `.gate/PROFILE.md`(목적), `python -X utf8 .gate/gate.py describe`(지금 구조), `.gate/library/*.toml`(빌려 올 상태와 절)을 읽는다.
3. 아래 신호를 찾는다. 신호마다 진단 자료의 수치나 파일을 근거로 적어 둔다.

| 신호 | 진단 자료에서 보는 곳 | 흔한 조정 |
|---|---|---|
| 새 산출물이나 폴더가 생겼다 | 저장소 변화의 새 파일, code 패턴 밖에서 바뀐 파일 | 그 산출물을 다루는 상태를 더하고 changed 조건으로 그 계획만 들르게 한다. code 패턴을 넓힌다 |
| 한 상태에서 자주 되돌아간다 | back으로 들어온 횟수, 검토 FAIL 이유 | 앞 상태에 빠진 검사를 더하거나 상태를 나눈다 |
| 형식만 채우고 지나간다 | 끝난 계획의 절 글자 수가 작고 머문 시간이 짧다 | 조건(max_files, option)을 붙여 작은 작업만 건너뛰게 한다. 빼는 것보다 조건을 먼저 고른다 |
| 같은 이유로 hook이 반복해서 막는다 | 막힌 기록의 상위 이유 | 규칙이 작업과 맞지 않으면 그 규칙을 고치고, 작업이 규칙을 피하려던 것이면 그대로 둔다 |
| 계획을 중간에 그만둔다 | 여기서 그만둠 | 그 상태의 할 일이 너무 크거나 앞 단계가 빠졌는지 본다 |
| 목적이나 단계가 바뀌었다 | PROFILE, 단계 변경 | 종류와 단계별 허용 종류를 다시 짠다. 목적이 바뀌었으면 사용자와 PROFILE을 먼저 고친다 |

조이는 변경(상태나 검사 더하기)은 근거 하나로 충분하다. 푸는 변경(상태나 검사 빼기, 검토 빼기, code 패턴 줄이기)은 진단 수치 근거가 있어야 하고, 같은 효과를 조건으로 낼 수 있으면 조건을 고른다.

## 2. 제안서

다음 번호로 `.gate/proposals/H###.md`를 쓴다(H001부터, 이미 있는 번호 다음).

````
# H### <한 줄 요약>

## 근거

진단에서 본 신호와 수치. PROFILE의 해당 절.

## 바꾸는 것

| 바꾸는 것 | 근거 |
|---|---|
| feature에 MIGRATE 상태 추가(migrations/가 바뀐 계획만) | 진단: migrations/ 새 파일 12개, P014와 P017이 TEST에서 back(마이그레이션 미적용) |

## 진행 중인 계획

진행 중인 계획은 시작할 때의 구조 버전을 끝까지 쓴다. 영향받는 계획과 그 이유를 쓴다. 없으면 "없음"이라고 쓴다.

## 새 구조

```toml
version = <지금 버전 + 1>
... 새 config.toml 전체 ...
```
````

새 구조에는 config 전체를 넣는다. 지금 config에서 출발해 바꾸는 곳만 고치고, 주석으로 바뀐 이유를 남기지 않는다(이유는 제안서에 있다). 새 상태는 todo, checks, sections를 모두 정의하고, 새 절은 [sections]에 body를 둔다. 라이브러리에 비슷한 상태가 있으면 빌려 와 고친다.

## 3. 검사와 승인

1. `python -X utf8 .gate/gate.py check-proposal H###`로 lint와 지난 계획 재생을 본다. 문제가 나오면 제안서를 고친다.
2. 통과하면 `check-proposal H### --review`로 검토자를 부른다(묻지 않고 한다). FAIL이면 이유를 보고 제안서를 고친다.
3. 사용자에게 보인다. "바꾸는 것" 표, 새 경로(H###.diag.md의 "새 구조 경로"), 영향받는 진행 중인 계획을 보여 주고 승인을 묻는다. 묻는 것으로 턴을 끝낸다.
4. 사용자가 승인하면 그 턴에 승인 문장을 그대로 넣어 적용한다.
   ```
   python -X utf8 .gate/gate.py adopt H### --approved "<사용자가 쓴 승인 문장>"
   ```
   guard가 그 문장이 이번 턴 사용자 입력에 있는지 본다. 사용자가 일부만 승인하면 제안서를 고쳐 1부터 다시 한다.
5. 출력된 순서대로 커밋한다. 하네스 커밋(`.gate/config.toml`, `.gate/history`)을 먼저 하고, 상태 파일과 제안서는 따로 커밋한다.

## 하지 않는 것

- 막힌 작업을 지나가려고 구조를 바꾸지 않는다. 그 작업이 규칙을 어긴 것이면 작업을 고친다.
- 진행 중인 계획을 새 구조로 옮기지 않는다. 새 구조는 다음 계획부터 쓴다.
- 사용자 승인 없이 adopt하지 않는다. 승인 문장을 지어내지 않는다.
