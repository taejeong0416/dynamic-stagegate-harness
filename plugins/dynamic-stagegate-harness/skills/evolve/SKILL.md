# 하네스 구조 다시 짜기

구조를 바꾸는 길은 제안서 하나뿐이다. 구조는 부품(`.gate/parts`)과 덮어쓰기(`.gate/local.toml`)를 조립한 결과(`.gate/config.toml`)이고, 셋 다 guard가 직접 편집을 막는다.

## 1. 진단

1. `python -X utf8 .gate/gate.py diagnose`를 돌린다. 상태별 기록, 검토 호출 수와 비용, hook이 막은 기록, `next`에서 막힌 이유, 저장소 변화, 부품별 상태가 나온다.
2. `.gate/PROFILE.md`(목적), `python -X utf8 .gate/gate.py describe`(지금 구조), `.gate/library/<이름>/part.toml`(가져올 부품)을 읽는다.
3. 아래 신호를 찾는다. 신호마다 진단 자료의 수치나 파일을 근거로 적어 둔다.

| 신호 | 진단 자료에서 보는 곳 | 흔한 조정 |
|---|---|---|
| 새 산출물이나 폴더가 생겼다 | 저장소 변화의 새 파일, code 패턴 밖에서 바뀐 파일 | 그 산출물을 다루는 상태를 더하고 changed 조건으로 그 계획만 들르게 한다. code 패턴을 넓힌다 |
| 한 상태에서 자주 되돌아간다 | back으로 들어온 횟수, 되돌아간 경로의 횟수와 이유, 검토 FAIL 이유 | 돌아간 상태에 빠진 검사를 더하거나 상태를 나눈다. 쓰이지 않는 경로는 back에서 뺀다 |
| 작은 종류로 큰 작업을 한다 | 그 종류의 끝난 계획이 적은 파일 수, code 패턴 밖에서 바뀐 파일 | 종류의 limit에 max_files나 changed 조건을 둔다 |
| 넘긴 뒤에 앞 절을 고친다 | 검토 FAIL 이유, back 이유 | 뒤 상태에 unchanged 검사를 더한다 |
| 형식만 채우고 지나간다 | 끝난 계획의 절 글자 수가 작고 머문 시간이 짧다 | 조건(max_files, option)을 붙여 작은 작업만 건너뛰게 한다. 빼는 것보다 조건을 먼저 고른다 |
| 같은 이유로 hook이 반복해서 막는다 | 막힌 기록의 상위 이유 | 규칙이 작업과 맞지 않으면 그 규칙을 고치고, 작업이 규칙을 피하려던 것이면 그대로 둔다 |
| 같은 검사에서 `next`가 자주 막힌다 | next에서 막힌 이유의 횟수와 계획 수 | 여러 계획에서 막히면 할 일이나 절 정의가 검사와 맞는지 보고 고친다. 한 계획에서만 반복되면 그 작업의 문제라 구조는 그대로 둔다 |
| 같은 상태의 검토가 연달아 FAIL한다 | `next`의 연달아 FAIL 안내, SessionStart 점검 이유, 상태 파일 검토 기록의 fails와 missing | 지적이 고칠 때마다 더 세밀한 경계 사례로 옮겨 가면 검토 지시문에 FAIL 기준(구현을 틀리게 하거나 확인할 수 없게 만드는 결함만 막는다)을 넣고, 세부 경계 사례는 테스트를 먼저 쓰는 상태나 PLAN의 확인할 동작으로 옮긴다. 같은 결함이 되풀이되면 할 일에 그 항목을 적게 한다 |
| 검토 비용이 계속 는다 | 검토 호출 표의 호출 수와 비용 | 지시문이 통째로 읽게 하는 큰 문서를 상태의 context에 옮기고 지시문을 `{context}` 발췌로 바꾼다. 문서 대조만 하는 검토는 review_model을 낮춘다 |
| 결과가 나온 뒤 코드가 바뀐다 | back 이유, 실행 상태의 되돌아간 경로 | 실행 상태에 code_unchanged 검사를 더한다 |
| 계획을 중간에 그만둔다 | 여기서 그만둠 | 그 상태의 할 일이 너무 크거나 앞 단계가 빠졌는지 본다 |
| 부품의 적용 조건이 바뀌었다 | 부품 절의 "조건이 거짓이 됐다", "조건이 맞는다" | 조건이 거짓이 된 부품은 빼고, 조건이 맞게 된 라이브러리 부품은 더한다. local.toml의 [answers]가 지금과 다르면 사용자와 답을 먼저 고친다 |
| 라이브러리에 부품의 새 버전이 있다 | 부품 절의 "라이브러리에 v2가 있다" | 프로젝트에서 고치지 않은 부품이면 폴더를 라이브러리 것으로 바꾼다. "프로젝트에서 고침"이면 고친 내용을 새 버전에 다시 넣는다 |
| 같은 분류의 결함이 여러 계획에서 나왔다 | 제안 초안의 "생성", 사고 기록 표 | 그 사고를 막았을 검사를 project 부품으로 쓴다. 기존 검사로 표현되면 `[[attach]]`에 그 검사를, 안 되면 부품 폴더의 checks.py에 새 검사를, 명령을 막아야 하면 `[[guard]]`를 쓴다. provenance에 사고 번호를 적는다 |
| 게이트를 지나 결함이 새어 나갔다 | 제안 초안의 "강화", 부품 성적의 새어 나간 결함 | 사고의 "드러난 상태"보다 앞 상태에 검사를 더한다 |
| 한 부품이 오탐만 낸다 | 제안 초안의 "완화", 부품 성적의 오탐과 진짜 막힘 | 검사 조건을 좁힌다. 빼는 것은 진짜 막힘이 없다는 수치가 있을 때만 한다 |
| 미판정 막힘이 많다 | 부품 성적의 미판정 | 막힌 기록의 이유를 사용자와 보고 진짜 막힘인지 정한다. 판정 없이 완화 근거로 쓰지 않는다 |
| 목적이나 단계가 바뀌었다 | PROFILE, 단계 변경 | 종류와 단계별 허용 종류를 다시 짠다. 목적이 바뀌었으면 사용자와 PROFILE을 먼저 고친다 |

조이는 변경(상태나 검사 더하기)은 근거 하나로 충분하다. 푸는 변경(상태나 검사 빼기, 검토 빼기, code 패턴 줄이기)은 진단 수치 근거가 있어야 하고, 같은 효과를 조건으로 낼 수 있으면 조건을 고른다. 사용자가 구조를 줄이라고 직접 요청한 변경은 그 말을 제안서의 "사용자 결정" 절에 옮기면 수치 대신 근거가 된다.

## 2. 제안서

다음 번호(H001부터, 이미 있는 번호 다음)로 사본을 만든다.

```
python -X utf8 .gate/gate.py propose H###
```

`.gate/proposals/H###/`에 지금 parts 폴더와 local.toml의 사본이 생긴다. 구조는 이 사본에서 바꾼다.

| 바꾸려는 것 | 사본에서 하는 일 |
|---|---|
| 라이브러리 부품 더하기 | `.gate/library/<이름>` 폴더를 사본의 `parts/` 아래에 복사한다 |
| 부품 빼기 | 사본의 `parts/<이름>` 폴더를 지운다 |
| 폴더 패턴, 서버 주소, 테스트 명령 같은 프로젝트 값 | 사본의 `local.toml`에 `[project]`, `[remote]`, `[review]` 키를 쓴다 |
| 이 프로젝트만의 상태나 검사 | 사본의 `parts/<새 이름>/part.toml`을 새로 쓴다. `origin = "project"`로 두고, `[states]`에 새 상태를, `[[insert]]`에 넣을 자리를, `[[attach]]`에 기존 상태에 더할 검사를 쓴다 |
| 라이브러리 부품의 내용 | 작은 값은 local.toml의 `[states.<상태>]`나 `[kinds.<종류>]`로 덮어쓴다. 그걸로 안 되면 사본의 part.toml을 고친다(고친 부품은 라이브러리 새 버전을 그대로 받지 못한다) |

part.toml의 키는 GATE.md의 "부품" 절에 있다. 그다음 `.gate/proposals/H###.md`를 쓴다.

````
# H### <한 줄 요약>

## 근거

진단에서 본 신호와 수치. PROFILE의 해당 절.

## 사용자 결정

- "하네스 극도로 간소화해" (2026-11-19)

## 바꾸는 것

| 바꾸는 것 | 근거 |
|---|---|
| feature에 MIGRATE 상태 추가(migrations/가 바뀐 계획만) | 진단: migrations/ 새 파일 12개, P014와 P017이 TEST에서 back(마이그레이션 미적용) |

## 진행 중인 계획

진행 중인 계획은 시작할 때의 구조 버전을 끝까지 쓴다. [project]의 code, files_section, max_visits, stop_states와 [review], [remote] exec_states도 그 버전을 따르므로, 새 구조는 다음 계획부터 적용된다. 영향받는 계획과 그 이유를 쓴다. 없으면 "없음"이라고 쓴다.
````

"사용자 결정" 절은 사용자가 이 구조 변경을 직접 요청했을 때만 두고, 아니면 뺀다. 사용자가 이 세션에서 쓴 문장을 큰따옴표 안에 그대로 옮긴다. `check-proposal`을 돌리면 guard가 인용마다 이 세션 사용자 입력에 있는지 보고, 없으면 막는다. 확인된 인용은 검토자가 빼거나 푸는 변경의 근거로 받으므로, 그 변경의 근거 칸에는 진단 수치 대신 "사용자 결정"이라고 쓴다. 검토자는 인용이 그 변경을 요구하거나 허락하는지만 본다.

새 구조는 사본을 조립한 결과라서 제안서에 config를 넣지 않고, version도 쓰지 않는다. 부품에는 주석으로 바뀐 이유를 남기지 않는다(이유는 제안서에 있다). 새 상태는 todo, checks, sections를 모두 정의하고, 새 절은 [sections]에 body를 둔다. 라이브러리에 비슷한 부품이 있으면 가져와 고친다.

parts 폴더가 없는 프로젝트는 `propose`를 쓰지 않는다. 제안서 끝에 "새 구조" 절을 두고 toml 블록에 `version = <지금 버전 + 1>`로 시작하는 새 config.toml 전체를 넣는다.

## 3. 검사와 적용

1. `python -X utf8 .gate/gate.py check-proposal H###`로 조립 문제, lint, 지난 계획 재생을 본다. 문제가 나오면 사본이나 제안서를 고친다. H###.diag.md의 "부품 변경" 목록이 의도한 것과 같은지 본다. "지난 계획 검사 재생"에서 사고가 난 계획이 새로 막히는지, 사고가 없던 계획이 새로 막히지는 않는지 보고, 그 결과를 사용자에게 함께 보인다. H###.diag.md의 "빼거나 푸는 변경" 목록에 있는 항목마다 "바꾸는 것" 표에 진단 수치 근거가 있는지 확인한다. 목록에는 [project], [review], [remote], [[stages]]의 푸는 변경과 방향을 정할 수 없는 "바뀐 설정"도 나온다. "바뀐 설정"이 검사를 푸는 쪽이면 그 근거도 표에 쓴다. 의도하지 않은 항목이 목록에 있으면 사본을 고친다.
2. 통과하면 `check-proposal H### --review`로 검토자를 부른다(묻지 않고 한다). FAIL이면 이유를 보고 제안서나 사본을 고친다. 통과한 뒤에 사본을 고치면 다시 검토받아야 한다.
3. 승인 방식(.gate/config.toml [project] approval)을 본다. 기본값 auto이면 묻지 않고 적용한다.
   ```
   python -X utf8 .gate/gate.py adopt H###
   ```
   바꾼 것과 근거 수치를 결정 기록(decisions_file)에 쓰고, 답에 "바꾸는 것" 표, 새 경로(H###.diag.md의 "새 구조 경로"), 영향받는 진행 중인 계획을 보고한다.
4. approval이 user이면 위 내용을 사용자에게 보이고 승인을 묻는 것으로 턴을 끝낸다. 사용자가 승인하면 그 턴에 승인 문장을 그대로 넣어 적용한다.
   ```
   python -X utf8 .gate/gate.py adopt H### --approved "<사용자가 쓴 승인 문장>"
   ```
   guard가 그 문장이 이번 턴 사용자 입력에 있는지 본다. 사용자가 일부만 승인하면 제안서를 고쳐 1부터 다시 한다.
5. 출력된 순서대로 커밋한다. 하네스 커밋(`.gate/config.toml`, `.gate/history`, `.gate/parts`, `.gate/local.toml`, `.gate/parts.lock`)을 먼저 하고, 상태 파일과 제안서는 따로 커밋한다.

## 하지 않는 것

- 막힌 작업을 지나가려고 구조를 바꾸지 않는다. 그 작업이 규칙을 어긴 것이면 작업을 고친다.
- 진행 중인 계획을 새 구조로 옮기지 않는다. 새 구조는 다음 계획부터 쓴다. 검토가 연달아 FAIL해서 구조를 바꿨고 그 작업을 새 구조로 이어야 하면, 그 계획을 abandon하고 `start --from`으로 새 계획을 시작해 앞 계획의 절을 옮긴다.
- check-proposal(lint, 재생, 검토자)을 통과하지 않은 제안서는 adopt하지 않는다. approval이 user이면 사용자 승인 없이 adopt하지 않고, 승인 문장을 지어내지 않는다.
- hook을 끄거나 우회하는 변경, 보호 파일 목록을 줄이는 변경은 제안하지 않는다.
